## 3. 채널별 목적과 운영 규칙

### 0_라운지
- 자유롭게 대화하는 경량 공간이며 봇은 채널 본문에 응답한다.
- 복합 업무를 실제로 진행할 때는 대화 원문을 이동하지 않고 필요한 맥락을 `1_업무요청`의 Task/Owner 흐름으로 연결한다.

### 1_업무요청
- 모든 업무 접수는 여기에서 시작한다.
- Demian은 요청을 분류하고 업무 유형을 결정한다.
- 유형 판정은 필수 의사결정 단계다.

### 2_프로젝트
- 본문: 업무 게시 및 상태판 성격으로 사용
- 협업: 해당 업무 thread에서 수행
- 1개 업무는 기본적으로 하나의 thread/task ID에 연결하도록 한다.

### 3_고객관리
- 본문: 해당 업무의 공지/상태 반영(필요 시)
- 협업: thread 중심
- 담당자 배정은 Demian 기준으로 운영한다.

### 4_기술-제안
- 본문: 안건/요지 게시용
- 협업: thread 중심
- 본문에서 결론을 완결하지 않고 thread에서 협업 결과를 정리한다.

### 5_리서치
- 회의 전 공통 근거를 수집·정리하는 독립 공간이다.
- 2/3/4의 의무 순차 단계가 아니다.

### 6_회의-이슈
- 중요한 안건이 생길 때 열리는 독립 회의실 채널이다.
- 2/3/4 진행 중 또는 다른 채널에서 중요한 안건이 발생하면 Sinclair가 Demian에게 회의 개설을 요청한다.
- Demian은 요청을 받아 6_회의-이슈 채널에서 회의실을 개설한다.
- Sinclair가 회의에 참여할 수 있다.
- 2/3/4 의무 단계가 아니다.

### 7_결과보고
- 2/3/4 처리 완료 후 Demian이 정리하여 게시한다.
- Staff bot은 직접 최종 결과 보고를 게시하지 않는다.

## 4. 본문/스레드 운영 원칙

- 2_프로젝트, 4_기술-제안은 **본문은 상태/안건 게시**, 실제 협업은 **thread에서** 수행한다.
- 1개 업무는 가능한 한 **하나의 thread/task ID**와 연결한다.
- mention 기반 호출/협업은 thread에서 최소 단위로 이뤄진다.
- 본문과 thread를 혼합해 하나의 업무 맥락이 분산되지 않도록 유지한다.

## 5. canonical 업무 흐름 (순차 파이프라인 아님)

```text
Telegram DM (Sinclair → Demian)
   └─ 1_업무요청 (필수 접수/분류)
         ├─ 2_프로젝트 (업무 유형 선택 시) ──┐
         ├─ 3_고객관리 (업무 유형 선택 시) ──┼─> 7_결과보고 (Demian 정리 게시)
         └─ 4_기술-제안 (업무 유형 선택 시) ─┘
```

- 5_리서치는 회의 전 근거 준비용 독립 공간이며 `1_업무요청 → 2/3/4`의 의무 단계가 아니다.
- 6_회의-이슈는 중요 사안 발생 시 별도 회의실로 개설되며, 모든 업무의 공통 필수 단계를 대체하지 않는다.

## 6. 시스템 경계(소스 오브 트루스)

- Hermes Kanban은 최종 업무 상태 원장이다.
- Slack은 협업 기록이며 업무 상태 Source-of-Truth가 아니다.
- 본 문서는 구현 입력 계약을 고정하는 운영 문서이며, 채널 생성/rename, config allowlist, Router/Meeting 엔진 라우팅, Telegram relay, 배포 완료를 선언하지 않는다.

## 7. 후속 구현에서 채널 ID 소비 시 변경 관리 원칙

1. **단일 진실 문서화**: 구현은 본 문서의 8개 매핑을 기준으로 참조해야 하며, 다른 값(테스트 채널/스레드 ID/임시 값)과 혼용하지 않는다.
2. **동일성 검증**: 구현 전후로 이름-ID 1:1 관계가 유지되는지 확인한다.
3. **변경 요청 발생 시**: 먼저 정식 채널 ID 변경 근거(요청 근거, 승인 기록, 반영 시점)를 남기고 본 문서를 갱신한 뒤 구현 변경 PR/작업을 진행한다.
4. **rollback 관점**: 변경이 불필요해지거나 실패 시, 이전 매핑 기준으로 즉시 되돌릴 수 있도록 과거 값 보존/로그를 남긴다.
